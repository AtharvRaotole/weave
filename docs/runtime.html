Runtime

Scripts are sandboxed; host tools are not. Hard deadlines and resource limits need a worker pool (docs/isolation.md); guarantees and the threat model are in docs/production.md. Trace v2 exact replay requires identical source (except trailing whitespace), tool declarations and stable invocation paths; old v1 traces are rejected. Host function code/remote schema identity is not attested by this manifest.

Effects

Untagged tools are irreversible. Pure and read calls start when their inputs are ready. Reversible calls wait for earlier observable work. Irreversible calls also wait until the whole script has arrived.

Timeouts

  • Async host tools are futures. Timeout and cancel drop the future.
  • Cooperative tools, including Python functions with a cancel parameter or **kwargs, receive a CancelToken. Weave stops waiting. It does not kill the thread.
  • Plain sync tools only abandon the wait. The thread is not signalled.
  • Engine(worker_pool=N) plus hard_deadline=True runs a sync Python tool in a spawn worker with cancellable queue acquisition. Timeout/cancel request local process termination and asynchronous replacement; this is not a real-time guarantee and cannot undo remote effects. Rust isolated start callbacks must be nonblocking.

A killed worker does not run finally. Work that already left the process is not undone. The function and its values must be pickleable, so define tools at module scope and keep Engine(...) inside if __name__ == "__main__". Closures are not sendable. One call occupies one worker; extra calls wait for a free slot.

Speculative pre-execution

Optional, and only for pure and read tools. A predictor proposes calls before the script is ready. Weave runs them and stores each result under the tool name plus the canonical arguments. When the script makes the same call, it uses the cached result. Sync, cooperative, and async tools can all be speculated. Reversible, irreversible, and duplicate predictions are rejected and not called. A prediction the script never uses is wasted work. This is the tool cache from Nichols et al., arXiv 2512.15834. It does not keep an inference engine resident.

Writes invalidate cached reads

Before a reversible or irreversible call runs, Weave drops every cached read whose read footprint overlaps the call's write footprint. A later read of the same call misses and runs live, so it sees the write. Reads earlier in the program still use the cache, because a write always waits for earlier reads. Pure results are never dropped. spec_invalidated counts the dropped entries.

Footprints are named resources. The default is every resource, so with no annotations any write drops every cached read. Narrow them to keep unrelated reads:

engine.tool("get_user", get_user, effect="read", reads=["users"])
engine.tool("get_order", get_order, effect="read", reads=["orders"])
engine.tool("rename_user", rename_user, effect="reversible", writes=["users"])
# rename_user drops cached get_user results; get_order results stay.

A footprint can name the arguments of the call: {0} is the first positional argument and {name} a keyword argument. Strings are inserted as-is, other values as their repr. With reads=["user:{user_id}"] on get_user and writes=["user:{user_id}"] on rename, rename("u1", ...) drops only the cached get_user("u1"). If a placeholder cannot be filled, the footprint widens to every resource, so a missing argument never keeps a stale read. In Python, engine.tool and @weave.declare(reads=..., writes=...) map parameter names to positions, so {user_id} works for positional calls.

@weave.declare(effect="read", arity=1, reads=["user:{user_id}"])
def get_user(user_id): ...

In Rust: ToolSpec::effect(Effect::Read).with_reads(Footprint::only(["users"])). In both MCP tool config formats: "reads": ["users"] or "writes": "*". The speculative call itself has already run against the old state and is not rolled back, so speculate only read tools that are safe to call early.

cache = engine.speculate_with(predictor, hint)
result = engine.run(source, speculation=cache)
result.spec_hits, result.spec_misses, result.spec_wasted

Sandbox and limits

Scripts come from a model, so Weave treats them as untrusted. What a script can reach:

  • No filesystem, network, process, or import access. The parser rejects import, def, class, lambda, while, with, global, and the rest of the statements outside the subset. Attribute access works only as a method call on a Weave value (string, list, dict methods implemented in Rust), so there is no __class__, __mro__, or __import__. Builtins are a fixed list (len, range, sorted, …); open, eval, exec, getattr, and globals do not exist. The interpreter never calls into Python or the OS.
  • Host tools are the only way out. A script can call only tools the embedder registered, with the effect and arity the embedder declared. Whatever a tool can do, the script can ask it to do. Review tools as you would an API you expose to the model.

Limits inside the runtime:

  • Steps (default 1,000,000): every executed statement and every loop iteration counts. Nested loops fail fast once the budget is spent.
  • Value size (default 16 MiB): string bytes plus container elements, counted through nested values. * repetition, str.replace, and str.join are refused before allocating when the result would pass a hard 256 MiB cap; other results are checked as they are built.
  • Wall time (default 30 s): measured from when the script first reaches the scheduler, so time spent waiting for streamed code is not counted. At the limit the run is cancelled and fails with time limit of Nms exceeded. Async futures are dropped and compute loops poll cancellation; a plain sync Python tool cannot be interrupted, so it is abandoned and keeps running in the background while the run returns.
  • Depth (fixed at 100): bracket nesting, block nesting, expression nesting, and value nesting. A lexical pre-check also rejects any statement with more than 1,000 operators before the parser runs, so deep or long expressions return an error instead of overflowing the stack.
engine.set_limits(max_steps=100_000, max_value_size=1_000_000, max_wall_time_ms=5_000)

In Rust: engine.set_limits(Limits::default().with_max_steps(100_000).with_max_wall_time(Duration::from_secs(5))).

Not covered: no process-wide memory cap or in-flight-tool budget. Source/output/compact-trace budgets default to 1/1/4 MiB, MCP frames to 8 MiB; see docs/budgets.md. Conversion, parsing and formatting may allocate before checks, and nothing limits what a host tool does once called. Errors from limits are ordinary runtime errors that try/except can catch.
